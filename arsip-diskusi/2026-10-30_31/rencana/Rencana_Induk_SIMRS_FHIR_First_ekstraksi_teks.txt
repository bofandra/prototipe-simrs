1. Ringkasan Eksekutif
SIMRS baru dirancang sebagai platform operasional klinis dan bisnis rumah sakit, bukan aplikasi rekam
medis yang sekadar menambahkan fitur bridging. Standar HL7 FHIR R4 menjadi bahasa interoperabilitas
klinis; transaksi internal dibangun sebagai model domain relasional di PostgreSQL. Tidak ada deployment
dedicated FHIR Server (misalnya HAPI) pada baseline. Backend Go menghasilkan, memvalidasi, menerima,
dan mengirim resource FHIR melalui adapter terpusat.

    Keputusan arsitektur yang sudah disepakati


      React + TypeScript untuk antarmuka semua modul.
      Go untuk backend bisnis dan integrasi.
      PostgreSQL sebagai sumber data otoritatif.
      Modular monolith sebagai bentuk deployment aplikasi awal.
      FHIR R4 sebagai acuan pemetaan klinis dan pertukaran data; bukan skema tabel wajib.
      Tanpa dedicated FHIR Server; kontrak API internal tetap REST/OpenAPI.
      Adapters khusus untuk SATUSEHAT, BPJS, HL7 v2 dan DICOM/PACS.
      Python hanya ditambahkan ketika analitik/AI membutuhkan runtime khusus.

Apa yang tidak termasuk baseline
Tidak membangun FHIR repository generic-search/history/transaction lengkap; tidak membangun PACS
maupun LIS analyzer engine dari nol; tidak menganggap FHIR Claim otomatis menggantikan kontrak
VClaim atau grouping INA-CBG; tidak memaksakan seluruh modul ERP ke resource FHIR; tidak
menduplikasi clinical source of truth demi keperluan integrasi.

sakit Indonesia dengan dukungan transaksi dan interoperabilitas nasional.

5.2 Deployment awal
      Satu backend Go sebagai deployment aplikasi utama; pekerjaan worker dapat dijalankan sebagai
       proses terpisah dari codebase sama.
      PostgreSQL utama dengan backup PITR, replica read-only bila dibutuhkan, dan akses database private

7.4 Integritas multi-RS

8.4 Resource apa yang tidak perlu disimpan sebagai JSON FHIR?
Status bed, biaya jasa dokter, jurnal akuntansi, reservasi stok, invoice settlement, payroll, itinerary tray
makanan, perintah pemeliharaan, inventory batch, dan audit user tidak memperoleh manfaat dari
disimpan sebagai satu blob resource FHIR. Simpan sebagai tabel transaksional lalu hasilkan representasi
FHIR bila memang ada use case interoperabilitas.

8.6 Validation gates
         Schema gate: resourceType, tipe element, cardinality dan status.
         Semantic gate: terminologi, code system, ucum, validasi nilai dan relasi.
         Profile gate: constraint FHIR profile / use case SATUSEHAT yang spesifik.
         Identity gate: patient IHS, org ID dan reference yang diizinkan.
         Workflow gate: status clinical final/verified; prior dependency sudah tersinkron.
         Delivery gate: log request, response, trace ID, retry eligibility dan reconciliation.

10. Blueprint Workflow End-to-End
10.1 Rawat Jalan
Appointment/queue → registrasi Encounter → asesmen/TTV → Condition/Procedure → order lab/rad/obat →
verifikasi hasil/dispense → tagihan → resume/discharge → export FHIR.

   Acceptance invariant: Satu encounter konsisten untuk seluruh order dan catatan.
   Acceptance invariant: Billing item hanya dibuat dari peristiwa layanan yang eligible.
   Acceptance invariant: Status encounter ditutup setelah workflow klinis dan administratif yang
    diperlukan.


10.2 IGD
Registrasi IGD → triase dan acuity → asesmen serial → order dan tindakan → observasi → disposition
pulang/RI/rujuk → discharge/transfer.

   Acceptance invariant: Triage timestamp dan author wajib.
   Acceptance invariant: Perubahan lokasi tidak menghapus rangkaian episode.
   Acceptance invariant: Status transfer/rujukan mengikuti aturan penerimaan target.


10.3 Rawat Inap
Admit → assign bed → nursing/care plan → visit/order → medication administration → transfer bed →
discharge planning → resume → discharge.

   Acceptance invariant: Tidak ada double occupancy aktif untuk bed yang sama.
   Acceptance invariant: MAR/BCMA tidak mengurangi stok tanpa jejak transaksi yang konsisten.
   Acceptance invariant: Addendum tersedia setelah dokumen ditandatangani.


10.4 Laboratorium
Order → specimen label/collect → accept/reject → analyzer/manual entry → QC → verification →
DiagnosticReport → charge dan export.

   Acceptance invariant: Hasil tidak boleh final sebelum verifikasi.
   Acceptance invariant: Order/specimen/result terhubung satu-ke-banyak.
   Acceptance invariant: Analyzer raw message dapat ditelusuri tanpa mengekspos PII di log umum.


10.5 Radiologi
Order → schedule → modality worklist (bila tersedia) → acquisition → PACS study → expertise → final report
→ charge.

   Acceptance invariant: StudyInstanceUID yang benar dan unik per studi.
   Acceptance invariant: DICOM pixels tetap di PACS; FHIR hanya metadata/link.
   Acceptance invariant: Revisi laporan memiliki version/provenance.

10.6 Farmasi & Obat
MedicationRequest → clinical verification → reservation/picking → compounding (bila ada) → dispense →

      Acceptance invariant: KFA / katalog klinis dibedakan dari SKU dan lot gudang.
      Acceptance invariant: Dispense reversal me-reverse ledger, bukan menghapus histori.
      Acceptance invariant: Aturan substitusi obat perlu persetujuan dan jejak audit.


10.7 Gizi Klinis dan Dapur
Nutrition assessment → NutritionOrder → diet kitchen planning → menu/material issue → production → tray

10.8 Billing dan Klaim
Verified service event → charge rule → invoice → payer split → payment/AR → coding/casemix → submission

      Acceptance invariant: No double-charge on replay.
      Acceptance invariant: Tarif memiliki effective date dan payer rules.
      Acceptance invariant: General ledger diposting dari transaksi finansial yang telah diverifikasi.


10.9 CSSD / Laundry

      Acceptance invariant: Batch/lot instrumen atau linen punya chain of custody.
      Acceptance invariant: Order layanan klinis dapat menjadi referensi, bukan skema fisik proses.


10.10 Consent dan Clinical Signing
Consent policy check → capture/renew/revoke → data access/clinical signature → audit event → disclose only
as permitted.

      Acceptance invariant: Signed document immutable; addendum traceable.
      Acceptance invariant: Revocation berdampak pada akses ke depan sesuai ketentuan.
      Acceptance invariant: No UI-only enforcement.


10.11 Integration BCP dan recovery
Jika SATUSEHAT tidak tersedia: transaksi klinis disimpan utuh, payload dievaluasi kembali melalui outbox,
dan pengiriman dilakukan setelah layanan pulih sesuai ketentuan use case. Jika ada mekanisme BCP
khusus antarpenyedia (mis. BPJS), hal tersebut menjadi adapter terpisah dengan spesifikasi tersendiri dan
tidak secara otomatis dijalankan dari retry umum.

Penutup
Blueprint ini mengunci pilihan FHIR-first tanpa FHIR Server khusus; tidak mengunci setiap tabel, endpoint
atau jadwal sebelum discovery. Keberhasilan desain ditentukan oleh konsistensi identitas, keamanan klinis,
ledger operasional, kontrak lintas domain, dan ketahanan integrasi. Aktivitas berikut yang harus dilakukan
adalah memperinci Master Feature Catalogue, membangun domain/event model, menulis mapping FHIR
berdasarkan Playbook resmi, dan mengimplementasikan satu vertical slice yang bisa diuji secara end-to-
end.

 Baseline untuk langkah berikut: G0 Feature Catalogue → G1 Architecture Foundation → G2 Clinical
 Vertical Slice.
